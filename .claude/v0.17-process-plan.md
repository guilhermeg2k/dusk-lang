# std/process v0.17: design proposal and implementation plan

Started 2026-11-17 on v017std. Planning only, requested by the user. API and backend recommendations below await discussion; no implementation.

## Goal and release slices

Launch external programs, collect their results and eventually interact with long-running children without blocking Dusk's VM thread. Prefer Zig std, consistent with the user's established backend preference. This is larger than the path/random modules because process lifetime, pipes and VM teardown must cooperate.

Recommend slice A: captured run, bounded output and deadline cleanup. Slice B: an explicit Child with configurable inherited/ignored/piped stdio, wait and termination. Agree whether both belong in v0.17 before implementation. Keep the public contract independent of backend choice.

## Slice A: captured execution

Proposed signature:

`run(args: []string, cwd: ?string = null, env: ?map[string, string] = null, timeout_ms: int = -1, max_output: int = 16777216) -> ProcessError!Result`

- args includes the executable at index zero. Empty lists, an empty executable, NUL in arguments/paths/environment, and invalid option values fail with InvalidArgument before starting a child. Empty non-executable arguments are preserved.
- Execute the program and argument array directly. No shell parsing, expansion, redirection or pipelines. Invoking a shell is explicit. Windows batch/command files require an explicit interpreter if necessary to uphold this contract; verify actual backend behavior.
- Default stdin is ignored/EOF so a tool cannot accidentally consume the parent's interactive stdin. Capture stdout and stderr independently, draining both concurrently from process start. Input text/bytes can be added later with simultaneous writing/draining, rather than prewriting a pipe that can deadlock.
- cwd changes only the child's directory. A relative cwd is resolved against the parent's working directory at submission, never via a process-global chdir.
- env is the complete replacement child environment when supplied; it is not an overlay. Null uses the VM's host-supplied environment snapshot, matching std/os; an absent embedding map means empty. Snapshot it into owned memory before handing work to another thread. Caller maps/strings can then be changed safely.
- Executable lookup is a separate decision from the environment passed to the child. Recommended: use the VM parent environment's PATH; replacement env does not change lookup. Installed Zig spawn uses ambient parent PATH, so honor the VM rule with explicit resolution/spawnPath if needed, or agree/document ambient lookup instead. Decide relative PATH/cwd and Windows executable-extension rules in the backend spike. Explicit executable paths bypass PATH lookup.
- timeout_ms = -1 means no deadline; 0 means an immediate deadline; values below -1 fail. The deadline starts at submission and covers launch, capture, child exit and cleanup initiation. On expiry, initiate forced termination of the owned direct child, drain or close pipes as appropriate and reap before returning TimedOut. Cleanup is not promised to finish at an exact wall-clock instant if the host kernel cannot complete it.
- max_output is a combined stdout+stderr cap, default 16 MiB; negative values fail. Zero permits empty output only. Enforce while reading, including large chunks, rather than collecting first. Exceeding it terminates/reaps the child and returns OutputTooLarge. Do not silently truncate a successful Result.
- Normal return requires the direct child to be reaped and both capture streams finished. Descendants may keep pipes open after that child exits; the deadline must remain effective until capture completes. Tree-wide termination is a separate feature.
- A nonzero exit is a result, not a ProcessError. Launch, I/O, timeout and cleanup failures use errors.

### Result and termination

`Result` fields: stdout: buffer, stderr: buffer, termination: Termination.

`Termination` is a union representing Exited(code: int), Signaled(number: int) or Unknown(status: int). Preserve exit versus signal termination instead of inventing an exit code from 128 plus signal. Signal/status numbers are host-specific; Windows termination normally reports an exit code. Preserve full backend status widths rather than truncating the public int to a byte. Do not treat stopped notifications as a completed child.

Methods:

- `is_success() -> bool`: true only for Exited(0).
- `stdout_text() -> ProcessError!string` and `stderr_text() -> ProcessError!string`: explicit UTF-8 decoding, returning InvalidUtf8 on invalid data. The original buffers remain usable. Capture never fails solely because output is binary.

Example shape (proposal, not runnable yet):

```dusk
import std/process
import std/io

func main() -> !void
    let result = try process::run(["git", "status", "--short"])
    io::print(try result.stdout_text())
    if !result.is_success() then
        io::eprint(try result.stderr_text())
    end
end
```

Suggested ProcessError set: InvalidArgument, NotFound, PermissionDenied, InvalidExecutable, ResourceLimit, TimedOut, OutputTooLarge, InvalidUtf8, Unsupported, Other. Finalize against actual backend errors. Runtime allocation failure follows existing conventions. A capture error cannot return while leaving an owned child running untracked.

## Slice B: interactive children (proposed next step)

Use `start`, avoiding confusion with the existing task-spawn prelude function.

`start(args, cwd = null, env = null, stdin_mode = Stdio.Ignore, stdout_mode = Stdio.Inherit, stderr_mode = Stdio.Inherit) -> ProcessError!Child`

Stdio modes: Inherit, Ignore, Pipe. Inherit refers to OS descriptors, not an embedded custom Dusk output writer; unsupported/custom embedding behavior must be explicit. Flush Dusk stdout/stderr before starting an inheriting child to preserve preceding output order.

Proposed Child operations:

| Operation | Behavior |
| --- | --- |
| wait(timeout_ms = -1) -> ProcessError!Termination | Park only the waiting task. Cache completed status for repeat calls. A wait timeout leaves the child running. Initially one waiter, with Busy for a concurrent second waiter. |
| kill() -> ProcessError!void | Request forced termination of this owned child; does not wait. A subsequent wait obtains termination. Idempotent after an observed exit. |
| stdin() -> ProcessError!PipeWriter | Return its piped stdin writer, or NotPiped. Closing sends EOF to the child. |
| stdout()/stderr() -> ProcessError!PipeReader | Return the corresponding piped reader, or NotPiped. |
| close() -> ProcessError!void | Release local resources after exit; Busy while the child still runs. Repeated close does nothing; wait after close is Closed. |

PipeReader/PipeWriter use the existing io::Reader/io::Writer shapes and text-versus-bytes naming. Opening/control errors are ProcessError; stream reads/writes use io::IoError. A child may exit before buffered output is read; exit must not discard buffered bytes. Process exit and pipe EOF are distinct events. Closing stdin/stdout/stderr does not itself kill the child. With exposed pipes, callers drain stdout and stderr concurrently; use captured run for automatic collection.

Do not expose a mutable Zig Child to two owners, an arbitrary kill-by-PID API, detached processes, or graceful termination under a misleading portable promise. A numeric pid accessor and graceful terminate can be discussed separately. Add Busy, Closed and NotPiped only when slice B is implemented.

## Backend decision: prove integration before choosing implementation

### Zig std first (preference)

Installed Zig 0.16 provides std.process.spawn/spawnPath, Child.wait, pipe files and process.run with dual-stream collection. Blocking operations must execute away from the VM thread.

A possible adapter owns each child in dedicated process-worker capacity and notifies the existing event loop through a completion queue plus uv_async_send. Do not park long-lived child waits in the shared libuv fs/DNS/trust-store worker pool: several children could occupy the pool while waiting for Dusk filesystem work. A dedicated worker approach needs an explicit concurrency/resource policy; allocating an unlimited thread per child is not an acceptable implicit default.

Libuv async callbacks run on the loop thread; sends may coalesce, so drain a synchronized completion queue rather than assuming one callback per completion. Workers must only touch owned host memory and publish outcomes; callbacks wake tasks, and VM resume constructs GC values. No worker can access Dusk heap objects.

Important findings from the installed std implementation:

1. process.run collects stdout/stderr concurrently, but accepts no stdin payload and ignores stdin. This matches initial run's default, not future input support.
2. Its timeout is passed to MultiReader.fill, followed by Child.wait with no deadline once pipes reach EOF. A child can close both outputs and continue running indefinitely. Convert relative timeouts to one absolute deadline and cover the final wait separately.
3. The Unix Child.kill path sends TERM and then waits. A TERM-ignoring child can prevent cleanup forever. Do not equate it with the proposed forced kill or use process.run as a drop-in deadline-safe runner.
4. process.run's deferred kill is also reached on capture errors. OutputTooLarge and timeout cleanup therefore need the same robust ownership/forced-termination solution.
5. Zig spawn's options environment does not control executable lookup; ambient parent PATH does. Preserve the agreed environment/lookup contract explicitly.

Required spike: demonstrate one-owner child management, cancellable/deadline-aware collection plus exit waiting, forced termination, and bounded teardown on Linux and the intended Windows path. Do not concurrently call wait and Child.kill on the same object. Prevent PID-reuse races between reaping and a delayed kill request. A small platform adapter for missing force/wait capabilities may be required even when launching with Zig std.

### Libuv alternative (requires design discussion)

uv_spawn, uv_process_t, exit callbacks and pipes fit the existing scheduler/stream layer directly, without a worker per child. This is the simpler event-loop integration, but uses more libuv than the user's preferred std-first approach. It also needs careful hand-written options/stdio ABI bindings or a minimal glue layer, plus host environment/PATH semantics validation.

Do not silently switch to this backend if the std spike fails; report the concrete limitation and discuss the tradeoff. Do not mix Zig and libuv reaping for the same child. Whichever backend wins, timeout/reaping tests are required before exposing run.

## Runtime lifetime and GC

- Copy argv, cwd and environment inputs into owned host allocations before parking/submitting. No Dusk pointers can survive into worker threads or OS callbacks.
- Child operation records are stable host allocations. Handles are opaque private fields on ordinary std structs, with stale-handle-safe table slots. Copies of a Child wrapper refer to the same OS child; they do not launch a new process.
- Use one synchronized owner/state machine for launching, running, terminating, exited and released states. A waiter timing out, an exit notification and shutdown cannot each complete the same parked call.
- A running owned child keeps its VM execution alive until reaped, even when no task is currently waiting. Open but idle completion handles alone must not keep the loop alive.
- On VM teardown, stop accepting submissions, cancel queued operations, forcibly terminate still-owned direct children, reap/join their owners, stop notifications, then close loop handles and free records. Completion notifications cannot target freed tasks or a destroyed loop.
- A child inherited outside this ownership model, or an externally managed process, is out of scope. No automatic process-tree termination guarantee.
- Extend WakePayload or add a dedicated process-result payload for termination plus two byte buffers; free every payload exactly once, including abandoned waits. Allocate all result components with correct heap maps and GC roots on resume. Native failures delivered after parking use absolute/relative error ids consistently.

## Phases after API/backend decisions

- [ ] P0: agree captured-only versus interactive scope, signatures, binary Result, environment/PATH policy, defaults and termination representation.
- [ ] P1: std-first integration spike. Verify VM responsiveness, safe timeouts after EOF, ignored TERM, output overflow cleanup and teardown. Decide backend based on evidence before committing to a full implementation.
- [ ] P2: module/registry/error mirrors, process records and wake payload, direct argv launch, cwd/environment snapshotting, termination and bounded dual capture.
- [ ] P3: total deadlines, output caps, forced cleanup/reaping, shutdown paths and supported-platform behavior. Captured run ships only once these pass.
- [ ] P4: interactive Child and pipe adapters if included; existing reader/writer traits, close/EOF/wait semantics, stale-handle and concurrency checks.
- [ ] P5: public docs/changelog/roadmap for shipped behavior, Debug and ReleaseFast suites, subprocess harness with external timeout, task tracking and granular commits. No benchmarks.

## Validation

Use a dedicated child fixture executable or fixture programs launched with an explicit runtime path. Avoid dependencies on installed shell tools for core tests. Every Dusk case is registered in src/test.zig; host harnesses have explicit commands and hard external timeouts.

- Exact arguments: spaces, empty strings, quotes, Unicode, literal shell metacharacters, missing executable, invalid launch options and Windows quoting/interpreter behavior.
- Child cwd/environment: no parent mutation, null versus empty replacement environment, VM snapshot policy, PATH/relative-path behavior and input mutation after submission.
- Termination: zero and nonzero exits, signal termination where supported, native status widths and cached wait. Nonzero exit is never a launch error.
- Pipes: child fills stdout and stderr beyond pipe capacity concurrently; stdin EOF; binary/invalid UTF-8 output; exit before EOF and EOF before exit; inherited-descriptor ordering.
- Deadlines: child closes both outputs then sleeps, writes continuously, ignores TERM, and leaves a descendant holding output open. Timeout must still complete according to direct-child policy, with no leaked/zombie direct child.
- Output limits: combined cap, zero/exact cap/one byte over, per-stream asymmetry and oversized read chunks; overflow cannot leave the child running.
- Responsiveness: Dusk timers, loopback networking and filesystem work progress while children run. Saturating process capacity cannot starve the fs pool or block a child that depends on Dusk I/O.
- GC/lifetime: collect while inputs are parked and results resume, hold results through later collections, close aliases, and fail VM execution while children run. Verify no callbacks touch freed memory and no handles/descriptors/workers remain owned after teardown.
- Interactive-only: concurrent waits, wait timeout without kill, kill racing normal exit, draining after exit, stdin close/EOF, double close and stale handles.
- Record actual Linux/Windows execution coverage; do not infer full cross-platform behavior from a compile-only check.

## Deferred

Shell convenience functions, pipelines, process groups/tree kill, detached children, arbitrary PID control, sandbox/resource limits, PTYs, replacement/exec, stdin payload for captured run, stderr merging, streamed run callbacks and public pid access until designed.
