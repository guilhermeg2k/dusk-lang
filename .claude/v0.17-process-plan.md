# std/process v0.17: design proposal and implementation plan

Started 2026-11-17 on v017std. Implementation requested 2026-11-17; both captured and interactive slices are included. User approved libuv for process lifecycle and pipes (2026-11-17). Public API and defaults follow the approved plan.

## Goal and release slices

Launch external programs, collect their results and eventually interact with long-running children without blocking Dusk's VM thread. Use libuv for launching, pipes, exit notifications, timers and termination. Use Zig std for validation, buffers and memory management. This is larger than the path/random modules because process lifetime, pipes and VM teardown must cooperate.

Both slices are implemented: captured run with bounded output/deadlines, and an explicit Child with configurable inherited/ignored/piped stdio, wait and termination. Keep the public contract independent of backend choice.

## Slice A: captured execution

Proposed signature:

`run(args: []string, cwd: ?string = null, env: ?map[string, string] = null, timeout_ms: int = -1, max_output: int = 16777216) -> ProcessError!Result`

- args includes the executable at index zero. Empty lists, an empty executable, NUL in arguments/paths/environment, and invalid option values fail with InvalidArgument before starting a child. Empty non-executable arguments are preserved.
- Execute the program and argument array directly. No shell parsing, expansion, redirection or pipelines. Invoking a shell is explicit. Windows batch/command files require an explicit interpreter if necessary to uphold this contract; verify actual backend behavior.
- Default stdin is ignored/EOF so a tool cannot accidentally consume the parent's interactive stdin. Capture stdout and stderr independently, draining both concurrently from process start. Input text/bytes can be added later with simultaneous writing/draining, rather than prewriting a pipe that can deadlock.
- cwd changes only the child's directory. A relative cwd is resolved against the parent's working directory at submission, never via a process-global chdir.
- env is the complete replacement child environment when supplied; it is not an overlay. Null uses the VM's host-supplied environment snapshot, matching std/os; an absent embedding map means empty. Snapshot it into owned host memory before launch/parking. Caller maps/strings can then be changed safely.
- Executable lookup is a separate decision from the environment passed to the child. Recommended: use the VM parent environment's PATH; replacement env does not change lookup. Verify libuv lookup rules on supported hosts; use explicit executable resolution if needed to honor the agreed policy. Settle relative PATH/cwd and Windows executable-extension rules during the launch-binding phase. Explicit executable paths bypass PATH lookup.
- timeout_ms = -1 means no deadline; 0 means an immediate deadline; values below -1 fail. The deadline starts at submission and covers launch, capture, child exit and cleanup initiation. On expiry, initiate forced termination of the owned direct child, drain or close pipes as appropriate and reap before returning TimedOut. Cleanup is not promised to finish at an exact wall-clock instant if the host kernel cannot complete it.
- max_output is a combined stdout+stderr cap, default 16 MiB; negative values fail. Zero permits empty output only. Enforce while reading, including large chunks, rather than collecting first. Exceeding it terminates/reaps the child and returns OutputTooLarge. Do not silently truncate a successful Result.
- Normal return requires the direct child to be reaped and both capture streams finished. Descendants may keep pipes open after that child exits; the deadline must remain effective until capture completes. Tree-wide termination is a separate feature.
- A nonzero exit is a result, not a ProcessError. Launch, I/O, timeout and cleanup failures use errors.

### Result and termination

`Result` fields: stdout: buffer, stderr: buffer, termination: Termination.

`Termination` is a union representing Exited(code: int), Signaled(number: int). Preserve exit versus signal termination instead of inventing an exit code from 128 plus signal. Signal/status numbers are host-specific; Windows termination normally reports an exit code. Preserve full backend status widths rather than truncating the public int to a byte. Do not treat stopped notifications as a completed child.

Methods:

- `is_success() -> bool`: true only for Exited(0).
- `stdout_text() -> ProcessError!string` and `stderr_text() -> ProcessError!string`: explicit UTF-8 decoding, returning InvalidUtf8 on invalid data. The original buffers remain usable. Capture never fails solely because output is binary.

Example shape (proposal, not runnable yet):

```dusk
import std/process
import std/io

func main() -> !void
    let result = try process::run(["git", "status", "--short"])
    io::print(try result.stdout_text())
    if !result.is_success() then
        io::eprint(try result.stderr_text())
    end
end
```

Implemented ProcessError set: InvalidArgument, NotFound, PermissionDenied, InvalidExecutable, ResourceLimit, TimedOut, OutputTooLarge, InvalidUtf8, Unsupported, Other, Busy, Closed, NotPiped. Runtime allocation failure follows existing conventions. A capture error cannot return while leaving an owned child running untracked.

## Slice B: interactive children (proposed next step)

Use `start`, avoiding confusion with the existing task-spawn prelude function.

`start(args, cwd = null, env = null, stdin_mode = Stdio.Ignore, stdout_mode = Stdio.Inherit, stderr_mode = Stdio.Inherit) -> ProcessError!Child`

Stdio modes: Inherit, Ignore, Pipe. Inherit refers to OS descriptors, not an embedded custom Dusk output writer; unsupported/custom embedding behavior must be explicit. Flush Dusk stdout/stderr before starting an inheriting child to preserve preceding output order.

Proposed Child operations:

| Operation | Behavior |
| --- | --- |
| wait(timeout_ms = -1) -> ProcessError!Termination | Park only the waiting task. Cache completed status for repeat calls. A wait timeout leaves the child running. Initially one waiter, with Busy for a concurrent second waiter. |
| kill() -> ProcessError!void | Request forced termination of this owned child; does not wait. A subsequent wait obtains termination. Idempotent after an observed exit. |
| stdin() -> ProcessError!PipeWriter | Return its piped stdin writer, or NotPiped. Closing sends EOF to the child. |
| stdout()/stderr() -> ProcessError!PipeReader | Return the corresponding piped reader, or NotPiped. |
| close() -> ProcessError!void | Release local resources after exit; Busy while the child still runs. Repeated close does nothing; wait after close is Closed. |

PipeReader/PipeWriter use the existing io::Reader/io::Writer shapes and text-versus-bytes naming. Opening/control errors are ProcessError; stream reads/writes use io::IoError. A child may exit before buffered output is read; exit must not discard buffered bytes. Process exit and pipe EOF are distinct events. Closing stdin/stdout/stderr does not itself kill the child. With exposed pipes, callers drain stdout and stderr concurrently; use captured run for automatic collection.

Do not expose raw process handles, an arbitrary kill-by-PID API, detached processes, or graceful termination under a misleading portable promise. A numeric pid accessor and graceful terminate can be discussed separately. Add Busy, Closed and NotPiped only when slice B is implemented.

## Backend: libuv (accepted 2026-11-17)

The existing event loop owns every process, pipe and timer. No process worker threads, shared-pool child waits, uv_async completion queue or std.process.Child wait/reaping are needed.

| Responsibility | Implementation |
| --- | --- |
| Launch | uv_spawn with owned argv/env/cwd and exactly configured stdio entries. |
| Exit | uv_process_t exit callback stores exit_status and term_signal. Libuv is the sole reaper. |
| Captured output | Two uv_pipe_t streams read concurrently into bounded host-memory capture sinks. |
| Interactive I/O | Process PipeReader/PipeWriter adapters over the existing Stream read/write/backpressure rules. |
| Deadline | uv_timer_t plus one absolute monotonic deadline, shared by exit and output completion. |
| Forced termination | uv_process_kill on the owned handle; no cached-PID uv_kill fallback. |
| Release | uv_close callbacks through HandleOwner after the child has exited. |
| Input/result plumbing | Zig std validation, checked buffer arithmetic and host-owned allocations; VM resume builds GC values. |

uv_spawn itself is synchronous setup; waiting for process exit and pipe I/O is asynchronous. A deadline can be checked before/after launch but cannot preempt that synchronous call or force a kernel to finish cleanup at an exact instant.

### Launch bindings

Add the process handle type, uv_spawn/uv_process_kill, exit callback and stdio options to tasks/uv.zig under organizational section headings. uv_process_t remains opaque with size from uv_handle_size. Mirror uv_process_options_t and uv_stdio_container_t only after checking their sizes/offsets against the pinned dependency headers on supported targets. Use a narrow glue adapter if the platform ABI cannot be represented reliably; no vendored dependency sources.

For created pipes, uv_spawn expects uv_pipe_init before launch and supplies the endpoints itself. Add a process-pipe construction path instead of using Stream.open(file), which assumes an existing descriptor. Flags are from the child's perspective: stdin is readable by the child; stdout/stderr are writable by it. Leave child-side pipes in their ordinary blocking mode; the parent's libuv endpoints remain asynchronous.

uv_spawn initializes its process handle even on launch failure: arrange the close callback and stable owner, close that handle on failure, and free memory only after close. Clean up every initialized pipe/timer from partial launch failures too. Install owner routing before any loop dispatch.

### Exit, output and failure rules

A process exit callback does not imply stdout/stderr EOF. Captured run succeeds only once the direct child has exited and both captures have ended. The timer stays active until that whole operation completes, including when descendants keep inherited pipe ends open.

Capture must consume incoming chunks eagerly into its bounded sink; do not leave captured data in the ordinary Stream high-water buffer and pause the child before the configured output cap. Interactive readers retain the existing backpressure rules. This distinction needs an explicit capture sink/consumer on Stream or a dedicated process capture pipe adapter; choose the smaller shared implementation without duplicating read rules.

Use one first-failure latch for timeout, capture-limit and read failures. On failure, stop/close capture pipes, request forced termination if the direct child still runs, wait for its exit notification, and complete the parked call once. Later EOF/exit/timer callbacks cannot overwrite the original failure or wake twice. A failed termination request must preserve process ownership and be reported; never free a live child record and silently leave it running.

A successfully spawned process handle must stay open until the exit callback; closing it early on Unix can prevent libuv from reaping it. This also changes EventLoop.deinit: terminate and drive owned children to exit callbacks before the existing generic uv_walk/close path. HandleOwner needs process and process-timer routing. Process records remain alive until all process/pipe/timer close callbacks and pending writes release their references.

Before a kill request, check observed exit state, then use uv_process_kill on that handle. Treat an already-exited race as an exit-wait condition; do not send a signal using a cached numeric pid. Test that timeout, explicit kill and normal exit cannot affect a later unrelated process.

## Runtime lifetime and GC

- Copy argv, cwd and environment inputs into owned host allocations before parking/submitting. No Dusk heap pointers may be retained in OS callback state; argv/env/path storage is owned host memory.
- Child operation records are stable host allocations. Handles are opaque private fields on ordinary std structs, with stale-handle-safe table slots. Copies of a Child wrapper refer to the same OS child; they do not launch a new process.
- Use one loop-owned state machine for launching, running, terminating, exited and released states. A waiter timing out, an exit notification and shutdown cannot each complete the same parked call.
- A running owned child keeps its VM execution alive until reaped, even when no task is currently waiting. Account for live owned children separately from parked task operations in EventLoop.hasPendingOperations, while preserving existing timer/stream counts. A captured operation remains pending after child exit until capture completes. Idle timers and closed/cached Child wrappers do not keep execution alive.
- On VM teardown, stop accepting submissions, cancel queued operations, forcibly terminate still-owned direct children, drive the loop until their exit callbacks, then close remaining loop handles and free records. Completion notifications cannot target freed tasks or a destroyed loop.
- A child inherited outside this ownership model, or an externally managed process, is out of scope. No automatic process-tree termination guarantee.
- Extend WakePayload or add a dedicated process-result payload for termination plus two byte buffers; free every payload exactly once, including abandoned waits. Allocate all result components with correct heap maps and GC roots on resume. Native failures delivered after parking use absolute/relative error ids consistently.

## Implementation phases after API scope is agreed

- [x] P0: agree captured-only versus interactive scope, signatures, binary Result, environment/PATH policy, defaults and termination representation.
- [x] P1: libuv bindings and process/pipe construction, launch/exit/failed-launch cleanup, HandleOwner routing and live-child accounting. Confirm ABI plus argv/cwd/environment/PATH behavior with a child fixture.
- [x] P2: module/registry/error mirrors, result wake payload and dual capture, binary Result/text methods and combined output cap. Keep the capture sink draining continuously.
- [x] P3: whole-operation deadlines, first-failure latch, uv_process_kill, exit/EOF races and VM shutdown before generic handle closure. Captured run ships only once cleanup/reaping tests pass.
- [x] P4: interactive Child and pipe adapters if included; existing reader/writer traits, close/EOF/wait semantics, stale-handle and concurrency checks.
- [x] P5: public docs/changelog/roadmap for shipped behavior, Debug and ReleaseFast suites, subprocess harness with external timeout, task tracking and granular commits. No benchmarks.

## Validation

Use a dedicated child fixture executable or fixture programs launched with an explicit runtime path. Avoid dependencies on installed shell tools for core tests. Every Dusk case is registered in src/test.zig; host harnesses have explicit commands and hard external timeouts.

- Exact arguments: spaces, empty strings, quotes, Unicode, literal shell metacharacters, missing executable, invalid launch options and Windows quoting/interpreter behavior.
- Child cwd/environment: no parent mutation, null versus empty replacement environment, VM snapshot policy, PATH/relative-path behavior and input mutation after submission.
- Termination: zero and nonzero exits, signal termination where supported, native status widths and cached wait. Nonzero exit is never a launch error.
- Pipes: child fills stdout and stderr beyond pipe capacity concurrently; stdin EOF; binary/invalid UTF-8 output; exit before EOF and EOF before exit; inherited-descriptor ordering.
- Deadlines: child closes both outputs then sleeps, writes continuously, ignores TERM, and leaves a descendant holding output open. Timeout must still complete according to direct-child policy, with no leaked/zombie direct child.
- Output limits: combined cap, zero/exact cap/one byte over, per-stream asymmetry and oversized read chunks; overflow cannot leave the child running.
- Responsiveness: Dusk timers, loopback networking and filesystem work progress while children run. Many running children must not occupy the fs worker pool or prevent a child from receiving a response from a Dusk service.
- GC/lifetime: collect while inputs are parked and results resume, hold results through later collections, close aliases, and fail VM execution while children run. Verify no callbacks touch freed memory and no handles/descriptors/process records remain owned after teardown.
- Interactive-only: concurrent waits, wait timeout without kill, kill racing normal exit, draining after exit, stdin close/EOF, double close and stale handles.
- Record actual Linux/Windows execution coverage; do not infer full cross-platform behavior from a compile-only check.

## Deferred

Shell convenience functions, pipelines, process groups/tree kill, detached children, arbitrary PID control, sandbox/resource limits, PTYs, replacement/exec, stdin payload for captured run, stderr merging, streamed run callbacks and public pid access until designed.

## Implementation notes

- Uses a narrow process_glue.c adapter for uv process options instead of mirroring ABI structs.
- Captured run returns a private record handle and builds Result in Dusk; interactive wait reuses the existing ints WakePayload. No new VM object kind or process-specific wake payload.
- Failed launches poll close callbacks before returning their native error.
- Parent VM PATH controls executable selection; empty/relative entries resolve against child cwd. Supplied env is a complete child replacement.
- Debug and ReleaseFast: 567/567 tests each; CLI lifecycle checks pass, including ignored TERM, close-before-exit, inherited-output order, VM failure cleanup and normal unawaited-child liveness. Windows ReleaseFast CLI cross-build succeeds; Windows runtime is not available here. Final fixture-style rerun and documented git --version example pass. Completed 2026-11-18.

- Windows environment exception: upstream v1.53.0 make_program_env fills required absent platform variables from the OS parent, even with explicit env. Documented rather than promising a strictly empty Windows block. Source: https://github.com/libuv/libuv/blob/v1.53.0/src/win/process.c#L595-L610
