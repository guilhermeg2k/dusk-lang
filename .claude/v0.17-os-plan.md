# std/os (v0.17): design proposal

Started 2026-11-17 on `v017std`, based on `v017` at `1225e8e`.
Status: proposal for discussion; API and scope are not yet agreed. No implementation.

## Goal and scope

Give command-line tools and services access to their execution environment and a way to shut down deliberately.

Recommended first slice: program arguments, environment reads, working-directory reads, and exit status. Recommended second slice: signal subscriptions for graceful shutdown. Environment mutation and changing directory are explicit scope decisions. Child processes belong in a separate design; path manipulation, random generation and terminal controls stay with their respective modules.

## Proposed API and behavior

Signatures below are design sketches, not implemented declarations. Error names are provisional.

| Operation | Proposed signature | Proposed behavior |
| --- | --- | --- |
| Program arguments | `args() -> OsError![]string` | Only arguments after the script path; excludes runtime executable and script path. An owned snapshot on every call. |
| Environment lookup | `env(name: string) -> OsError!?string` | Missing is null; an empty value is an empty string. Reject invalid names and invalid UTF-8. |
| Working directory | `cwd() -> OsError!string` | Current absolute process working directory; not the entry module's directory. |
| Default exit status | `set_exit_code(code: int) -> OsError!void` | Execution continues; status is used on normal completion of all tasks. A runtime failure still exits unsuccessfully. Recommend accepting 0 through 255. |
| Environment update (optional) | `set_env(name: string, value: string) -> OsError!void` | Changes process environment for all tasks. |
| Environment removal (optional) | `unset_env(name: string) -> OsError!void` | Missing name is a successful no-op. |
| Change directory (optional) | `chdir(path: string) -> OsError!void` | Process-wide; affects all future relative filesystem operations. |

Suggested initial OsError vocabulary: InvalidArgument, InvalidUtf8, NotFound, PermissionDenied, Unsupported, Other. Finalize it against the actual operations before implementing; do not silently replace invalid text. Allocation failure follows existing native conventions.

Arguments need a documented CLI contract: `dusk program.dsk arg1 --flag` exposes `["arg1", "--flag"]`; argument parsing stops at the script path. Embedded runs receive arguments explicitly, defaulting to empty. Keep argument storage alive across execution and allocate returned values using the normal GC rules. Script and executable paths, if later exposed, get separate functions.

Environment names reject empty strings, NUL and `=`; values reject NUL. Lookup uses host case rules. A snapshot cannot change when a caller mutates a returned value. Enumeration of the entire environment is optional later.

Changing directory is particularly consequential: filesystem jobs already execute on pool threads, so a concurrent chdir can race relative path resolution. Prefer omitting chdir initially. If included, decide whether every path is made absolute at submission, and specify how it interacts with SSL_CERT_FILE / SSL_CERT_DIR and other relative configuration paths. Do not promise task-local working directories.

## Exit policy to decide

Recommend `set_exit_code` first: it allows ordinary resource cleanup and avoids adding an expression that never returns when Dusk has no public never-returning type.

An immediate `exit(code)` is a separate decision. If desired, define its static control-flow behavior, how it stops all tasks, flushing of stdout/stderr, native resource teardown, and what an embedded host receives. Avoid terminating the host process from a builtin. Stopping tasks is not equivalent to executing user cleanup; cancellation and defer semantics are separate work.

Normal completion means the runtime finishes according to its existing task-liveness rules. Setting an exit code must not suppress runtime failures or unhandled task failures. Decide whether nonzero codes from several tasks use last-write-wins (recommended for an explicitly process-global setter).

## Signals: recommended design direction

Prefer an explicit subscription over a bare one-shot wait: subscribe before serving, so a signal between registration and waiting can be retained. Proposed shape: `watch_signal(signal) -> OsError!SignalStream`, with `wait()` and idempotent `close()`. A subscription has one waiter; another concurrent waiter fails with Busy. Closing wakes a parked waiter with Closed. Final signatures/error ownership remain open.

Start with Interrupt and Terminate where supported. Do not expose raw signal numbers as a portable API. Unsupported signal/platform combinations fail explicitly. On Windows, libuv can receive console Interrupt, but Terminate watchers never receive notifications; do not present Terminate as portable there.

Specify one pending notification per subscription, coalescing repeated arrivals rather than promising a count. Separate subscriptions receive their own notification. Default signal behavior remains in place when no subscription is active; stopping the last subscription must be tested. Decide what a second Interrupt should do while cleanup is running.

Runtime ownership follows timers and streams: C-side subscription memory, HandleOwner dispatch, loop callbacks only record notifications or wake tasks; no Dusk execution or allocation in callbacks. Close handles asynchronously before freeing memory; parked waiters stay GC roots. Active subscriptions/waits and task liveness must be specified, including teardown when the main task finishes.

## Implementation sequence after decisions

1. Agree scope, names, error set and exit policy.
2. Pass arguments and normal exit status through CLI, Dusk embedding interface and VM; register std/os and its error mirror.
3. Implement arguments, environment lookup and cwd using the existing runtime allocation and platform abstraction conventions. Keep libuv calls in the task/runtime abstraction layer, not in builtin wrappers.
4. Add optional mutations only if agreed, with the process-global semantics above.
5. Design and implement signal ownership, registration, waiting and close; preserve existing behavior when unused.
6. Add public reference documentation and a user-visible changelog only when behavior exists.

## Validation plan

- Register every Dusk test in src/test.zig; use the existing extern/binding and mirrored-error tests.
- Arguments: empty list, order, spaces, flags after the script, Unicode, invalid host bytes and fresh returned arrays. Use a subprocess harness to exercise actual CLI forwarding.
- Environment: missing versus empty, Unicode, invalid names/values, invalid host bytes and any agreed mutations. Isolate process-global tests in child processes.
- Cwd: absolute result and host errors; if chdir is accepted, isolate tests and cover concurrent fs job semantics.
- Exit: child-process checks for default zero, configured status, invalid status, buffered output and runtime-failure precedence. Embedded execution must return control to its host.
- Signals: registration before waiting, coalescing, multiple subscribers, Busy, close while waiting, repeated close, teardown and platform support. Use a child readiness handshake, not timing sleeps; an external timeout catches hangs.
- Run Debug and ReleaseFast suites after implementation. No benchmarks are needed for planning.

## First discussion

1. Scope: start with args/env/cwd/exit status, or include signals in the first implementation?
2. Mutations: read-only environment and cwd first, or include set_env/unset_env/chdir?
3. Exit: set_exit_code only, immediate exit too, or a different public API?
