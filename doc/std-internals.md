# Standard library internals

How the standard library's modules work inside the runtime: fs jobs on libuv's thread pool, streams (stdin, TCP connections and opened files), TCP, TLS, the HTTP client and server, compression, time and time zones, the OS context and signals, random numbers, child processes, and serialization. It describes the code as of v0.17 (in development). The VM underneath (values, the interpreter, natives, the garbage collector, tasks and the event loop) is in [vm-internals.md](vm-internals.md), and the modules' Dusk API is in [std-ref.md](std-ref.md).

## 2. fs jobs

Every `std/fs` call is one `FsJob` (`src/runtime/io/fs/fs_job.zig`), run with `uv_queue_work` on libuv's thread pool:

1. The native copies its paths (NUL-terminated) and, for writes, the bytes out of the GC heap into the job, since the GC moves objects. `EventLoop.startFsJob` queues the job, counts it in `pending_operations`, and the native parks.
2. `onFsJobWork` runs on a pool thread. It calls `FsJob.runOnPoolThread`, which makes the blocking calls back to back as **synchronous** `uv_fs_*` calls (no callback), so libuv still handles the platform differences. `fs::read` is one job doing open, fstat (a size hint), read until EOF, close and the UTF-8 check. Recursive `make_dir` and `delete` loop inside the same job. One job means one round trip through the pool per Dusk call, where the usual chain of async libuv requests would take one per step. libuv's sync fs calls don't register with the loop, so they're safe from a pool thread.
3. `onFsJobDone` runs on the loop thread: it uncounts the job, turns its result into a `WakeResult` (`FsJob.takeWakeResult`, moving the C memory into the payload), calls `Scheduler.wake` and frees the job.

**Thread rule.** The pool thread only touches the job's own memory (paths, input, result fields), allocated with the C allocator. It never touches the VM, the GC heap or the scheduler.

**Errors** are mapped by name with `uv_err_name` (`ENOENT` to `NotFound`, `EACCES`/`EPERM` to `PermissionDenied`, `EEXIST`, `EISDIR`, `ENOTDIR`, `ENOTEMPTY`, anything else to `Other`), since libuv's error numbers differ per OS. The Zig enum `FsError` mirrors the error set in `std/fs.dsk` (a test checks names and order), and the wake sends its variant as a relative error id ([vm-internals](vm-internals.md) 11.3).

**Details.** Writes open with `WRONLY | CREAT | TRUNC` (or `APPEND`), taken from `std.posix.O` on POSIX and from the C runtime's `_O_*` values on Windows. `read_dir` uses `uv_fs_opendir`/`uv_fs_readdir` rather than `uv_fs_scandir`, which sorts the names. Recursive `delete` on POSIX runs in `fs_glue.c` (`dusk_fs_delete_tree`), using an iterative heap stack of open directory handles (`unlinkat` first for files/symlinks, then `openat` with `O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC` for directories) capped at 64 open directory fds, so it never follows symlinks (even under concurrent races) and never overflows the worker stack; Windows uses an iterative heap-stack walk over libuv's `opendir`/`readdir`. `stat` runs `lstat` first and `stat` only for a link, so the other fields describe the link's target.

## 3. Streams (stdin, TCP connections and files)

`io::stdin()` calls `EventLoop.openStdin`, which opens a `Stream` (`src/runtime/io/stream/stream.zig`) on the first call and returns its stream id. Streams, listeners and certificates live in `SlotTable`s (`tasks/loop/slot_table.zig`), and the Dusk side refers to them by id (`stream_id`, `listener_id`, `certificate_id`): an id is the slot index in its low 32 bits and the slot's version above, bumped when the slot is freed, so closed slots are reused without an old id ever reaching the new occupant (it finds nothing and fails with `Closed`). The Dusk value (`io::Stdin`) only holds that id in its file-only `stream_id` field, and the `io::Stdin` methods are Dusk code calling file-only natives with it. The fd is `VM.stdin_fd` (0 unless a test passes a pipe or a file). `uv_guess_handle` picks the kind:

| Kind | Opened as | Reads with |
|---|---|---|
| `tty` | `uv_tty_init` | `uv_read_start` |
| `pipe` | `uv_pipe_init` + `uv_pipe_open` | `uv_read_start` |
| `file` | the fd itself | 64 KiB `read_chunk` fs jobs (2), one at a time |
| `tcp` | `uv_tcp_init` (by connect or accept, 4) | `uv_read_start`, through the TLS layer when `tls_layer` is set (5) |
| `closed_input` | — | always at the end |

A `Stream` lives in C memory: the bytes read so far (a byte array and a read offset; consumed bytes are dropped by moving the rest down once the offset passes half), the end and failure flags, at most one `waiter` (the parked task and what it asked for), and an optional timer.

**One rule for every read.** `Stream.readyOutcome(mode)` decides whether a read (`bytes`, `exact`, `line`, `all_text`, `all_bytes`, and the HTTP modes of 6) can complete now, and returns the data (a slice of the buffer and how much to consume), the end, or an error. The rules themselves live on `ReadSource` (the available bytes, whether the input ended, its failure), so the same code reads a socket's buffer and an HTTP body after decoding. The native calls it first and, when it's ready, builds the string or buffer right there with no park. That's the common case when lines come from a pipe. Otherwise it parks the task as the waiter (or fails with `Busy` if there already is one), turns reading on, starts the timer for `timeout_ms`, and counts one pending operation. Before parking on stdin, it flushes stdout, so prompts show up.

**Callbacks.** libuv's `onAlloc` hands out free space at the end of the buffer, and `onRead` appends to it, or records the end (`UV_EOF`) or a failure. A finished `read_chunk` job does the same through `Stream.finishChunk`. Then `serveWaiter` runs `readyOutcome` for the waiter: if the read can complete, it copies the result into a payload ([vm-internals](vm-internals.md) 11.3), consumes it, stops the timer and wakes the task. If no task waits and 1 MiB or more is buffered, reading stops (`uv_read_stop`), so a fast writer fills the OS pipe and slows down instead of filling memory. The next read turns it back on.

**Timeouts and one wake per wait.** Each stream has one timer handle, made on its first timed read and reused. Data (`serveWaiter`), the timer (`onReadTimeout`) and `close()` all clear the same `waiter`: the first one wakes the task and stops the timer, and the others find no waiter and do nothing. Everything runs on the loop thread. A timed-out read consumes nothing.

**Writing (TCP).** Every TCP stream has `TCP_NODELAY` on (`uv_tcp_nodelay` in `Stream.openTcp`, which libuv applies when the socket is attached by accept, connect or `uv_tcp_open`), so a small write goes out at once instead of waiting for the peer to acknowledge the previous one. `Stream.write(task, data)` first tries `uv_try_write` straight from the string's or buffer's bytes in the GC heap: the call is synchronous, so the GC can't move them meanwhile, and a small write finishes with no park and no copy. Whatever the socket didn't take is copied into a `WriteRequest` (C memory, with its own `uv_write_t`) and queued with `uv_write`; the task parks and `onWrite` wakes it when the system has taken everything (`ECANCELED`, from a close, becomes `Closed`). libuv's `uv_try_write` returns `EAGAIN` while any write is queued, so a later write never jumps ahead of an earlier one: writes from several tasks go out whole and in call order. `requests_in_flight` counts queued writes (and a pending connect, 4), and a request keeps its own allocator so it can free itself after the stream is gone. With a write timeout (`setWriteTimeout`, from `TcpConn.set_write_timeout`, the HTTP server's `write_timeout_ms` and the client's remaining `timeout_ms`), a third timer per stream (`HandleOwner` kind `stream_write_timer`) runs while writes are queued (`queued_writes`): it starts when a write is queued, restarts each time one finishes with more still queued (`finishQueuedWrite`), and stops when none are left. When it fires (`onWriteTimeout`), the stream is closed through `EventLoop.closeStream`; the queued writes come back with `ECANCELED` and `has_write_timed_out` turns that into `TimedOut`.

**Closing and freeing.** `close()` wakes a waiter with `Closed`, stops reading, closes the stream handle and the timer, and clears the table slot. `EventLoop.stdin_stream_id` keeps the old id, so later `io::stdin()` reads fail with `Closed`. The `Stream` is freed only when it's closed, its open handles (`open_handles`: the stream handle and any timers — read, handshake, write) have all reported back to `onHandleClosed`, no chunk job is running (a job still on the pool writes into the stream when it finishes), and no connect or write request is in flight (libuv calls their callbacks with `ECANCELED` before the handle's close callback). At exit, `releaseAtExit` marks every stream closed and the loop's handle walk closes what's left. File streams close their fd only when it's above 2; libuv never closes stdio fds either.

**Missing stdio fds.** libuv asserts that it never closes fds 0 to 2. If the program starts with one of them closed, the loop's own fds would get those numbers, so `main.zig` opens `/dev/null` in their place first; closed stdin then reads as the end of the input.

**Open-file limit.** Every connection, listener and opened file holds one fd, and many systems start processes with a soft limit of 1024 open files, well below the hard limit. On POSIX, `main.zig` raises the soft `RLIMIT_NOFILE` to the hard limit before anything opens (on macOS to at most `OPEN_MAX`, which `setrlimit` refuses to exceed). A failure leaves the limit unchanged. Child processes inherit the raised limit.

**Writers.** `io::stdout()` and `io::stderr()` don't use libuv: their methods go through `Stdio` like `io::print`, but `Stdio.tryWriteBytes` / `tryFlush` return the error (`BrokenPipe` becomes `IoError.BrokenPipe`) instead of ending the program, and drop the bytes that couldn't be sent so the exit flush doesn't fail again.

**Terminals.** `Stdin.set_raw` calls `Stream.setTerminalMode`, which needs a `tty` stream (`NotTerminal` otherwise) and calls `uv_tty_set_mode` on its handle with `raw` or `normal`. On Linux and macOS libuv saves the terminal's settings on the first change and puts them back when that handle closes, and `uv_tty_reset_mode` puts them back from anywhere (it is safe even inside a signal handler). On Windows only `uv_tty_reset_mode` restores the console's input mode. Turning raw mode on sets `EventLoop.has_used_raw_terminal`, and `EventLoop.restoreTerminal` then calls `uv_tty_reset_mode`: `VM.run` calls it before printing a runtime error, `reportUnhandledTaskErrors` before printing a task error, and `EventLoop.deinit` first thing. Libuv opens the terminal again by its name (`/dev/tty...`) instead of using fd 0, so the non-blocking mode it sets doesn't reach other programs sharing the terminal.

`Stdout.size` / `Stderr.size` call `~terminal_size_numbers(fd)`, which returns `null` unless the output is a terminal (for stdout, `Stdio.is_stdout_terminal`, so a custom writer never is). `EventLoop.terminalSize` keeps one output-only `uv_tty_t` per output in `EventLoop.terminal_outputs` (`io/terminal.zig`, `HandleOwner` kind `terminal_output`), made on the first call and closed at shutdown; it never writes, it only answers `uv_tty_get_winsize`. A size of 0 (some pseudo-terminals report it) counts as unknown. On Windows, `main.zig` turns on escape sequences for stdout and stderr at startup (`File.enableAnsiEscapeCodes`), since output goes through `Stdio`, not libuv.

## 4. TCP

`std/net` (`src/runtime/builtins/std/net.dsk` + `net.zig`) keeps the same shape as stdin: `net::TcpConn` holds a stream id and `net::TcpListener` a listener id in a file-only field, and their methods call file-only natives. A connection is a `tcp` `Stream` in `EventLoop.streams`, so it reuses the stream reads and writes (`net.zig` binds its `~stream_*` externs to the natives in `io.zig`). Listeners have their own table, `EventLoop.listeners`. Both tables are released at exit.

**Opening.** `tcp_connect` and `tcp_listen` both create an `OpenRequest`:

1. An IP address is parsed with `uv_ip4_addr` / `uv_ip6_addr`. Anything else is looked up with `uv_getaddrinfo` on libuv's thread pool, and the task parks.
2. `openNextAddress` tries each address in order. For a connect, it opens a new `tcp` stream for each attempt and calls `uv_tcp_connect` (a handle can't be reused after a failed connect); for a listen, it opens a new `Listener` and calls `uv_tcp_bind` (with `UV_TCP_REUSEPORT` when `reuse_port = true`) + `uv_listen`. A failed attempt closes what it opened and moves on; when no address is left, the last failure is the result.
3. The result is an `OpenProgress`: `opened` or `failed` right away (an IP address to listen on, a bad address) returns from the native with no park; `waiting` parks the task, and the callbacks (`onLookup`, `onConnect`) finish it with `Scheduler.wake`. A connect stream goes into the table before connecting, so the exit cleanup can release it, but its index only reaches Dusk on success. On success (and on accept) the stream saves the peer's address (`uv_tcp_getpeername`), and the Dusk side copies it right away into `TcpConn`'s file-only `remote_host` / `remote_port` fields (`net::open_conn`), so `remote_address()` needs no native call and still works after the stream is freed.

`timeout_ms` adds a timer to the request. When it fires first, it cancels the lookup (`uv_cancel`, which only works while the job hasn't started) or closes the attempt's stream, and wakes the task with `TimedOut`. The callbacks that still arrive find the request finished, or the loop shutting down (`EventLoop.is_shutting_down`, set first in `deinit`), and only clean up: the request is freed once the lookup, the attempt and the timer's close have all reported back (`destroyIfDone`).

**Accepting.** libuv accepts one connection per poll and stops watching the socket until `uv_accept` takes it. `onConnection` only records that libuv holds one (`has_unaccepted_connection`) and serves the waiter, if there is one. `Listener.takeReadyConnection` is the one rule for `accept`, used by the native (no park when a connection is ready) and by `serveWaiter`. When its queue (`ready_connections`) is empty, `queueReadyConnections` takes libuv's connection (`uv_accept` into a new `tcp` stream), then, outside Windows, keeps accepting straight from the listening socket (`uv_fileno`, `accept4` with non-blocking and close-on-exec, wrapped with `uv_tcp_open`) until the system has none left or 64 are queued, so a burst is taken in one go instead of one connection per scheduler round. Draining only happens on behalf of a task calling `accept`, so connections nobody accepts still wait in the system's queue (`backlog`); `close()` closes the queued ones. One task waits at a time (`Busy` otherwise); the listener's timer (reused, like a stream's) and `close()` clear the same waiter, so only one of them wakes it.

**Errors** are mapped by name: connect, bind and lookup failures to `NetError` (`ECONNREFUSED`, `EADDRINUSE`, the `EAI_*` lookup errors to `HostNotFound`...), stream failures to `IoError` (`EPIPE` to `BrokenPipe`, `ECONNRESET`, `ECANCELED` to `Closed`). SIGPIPE never ends the process: the `std.Io.Threaded` that Zig's start code creates for `main` installs a do-nothing handler for it (Dusk sets none itself), so a write to a closed socket returns `EPIPE`. `accept` fails with `IoError` while `tcp_connect` fails with `NetError`: each extern's `error_base` comes from the set in its own signature, and the wakes send relative ids ([vm-internals](vm-internals.md) 11.3).

## 5. TLS

**mbedTLS through a C glue file.** mbedTLS 4.1.1 (the long-term-support line) comes from the `duskilang/mbedtls` fork through `build.zig.zon`, like libuv (`duskilang/libuv`): its releases are `.tar.bz2` files Zig's package fetcher can't read and its git tags lack the generated sources, so the fork's `dusk/v4.1.1` branch holds the release contents unchanged plus a `build.zig`, which compiles it with the default configuration (`DUSK.md` there has the upgrade steps). Its structs have sizes and layouts only C knows (they depend on the configuration), and its constants are macros, so Zig never touches them: `tls_glue.c` owns every mbedTLS object (`mbedtls_ssl_context`, `mbedtls_ssl_config`, certificates, keys, the session-ticket key) and exposes about 20 functions with opaque pointers and its own `DUSK_TLS_*` status codes (done, want more, failed, untrusted, expired, wrong host, out of memory, invalid, end). `tls.zig` declares them by hand, like `uv.zig`. `psa_crypto_init` runs once, on the first TLS call. mbedTLS isn't built thread-safe, so it's only called from the loop thread.

**Memory I/O.** Each session has two byte queues in the glue, given to `mbedtls_ssl_set_bio`: encrypted bytes from the socket go into `input` (`dusk_tls_feed`), and mbedTLS's output collects in `output`, which Zig sends and then consumes. mbedTLS never touches the socket. When mbedTLS returns "want read" while `input` still holds bytes, it means "call again" (it does that after a TLS 1.3 post-handshake message such as a session ticket), so `dusk_tls_read` and `dusk_tls_handshake` call again while input is queued, up to 8 calls in a row without progress.

**The stream side.** A TLS stream is a `tcp` stream with `tls_layer` set (`TlsLayer`: the session, client or server role, handshake state `pending` / `running` / `done` / `failed`, the `NetError` it failed with, and the tasks waiting on it). `onAlloc` hands libuv the layer's 64 KiB `cipher_scratch`, and `onRead` feeds it to the session (`receiveCiphertext`), then either steps the handshake or decrypts everything it can into the plaintext `buffered` (`decryptAvailable`), after which the usual `serveWaiter` / `readyOutcome` rules from 3 run unchanged. A peer's `close_notify` is the end of input. A write encrypts with `dusk_tls_write` and sends the output through `sendBytes`, the same `uv_try_write`-then-`WriteRequest` path plain writes use, so the ordering and backpressure rules hold. Handshake records and alerts go through `sendBytes` with no task: their `WriteRequest` wakes nobody and records a failure instead. A stream can also carry a `tunnel_layer` under `tls_layer`: TLS to an `https://` proxy, with the server's TLS running inside its `CONNECT` tunnel. `~stream_start_tunneled_tls` (http only; `start_tls` on a TLS stream stays a runtime error) moves the finished proxy layer into `tunnel_layer` (inside `Stream.startClientTls`, when `canMoveTlsIntoTunnel` allows it: the proxy handshake is done and no tunnel exists yet) and starts the server's layer on top, fed first with the tunnel plaintext already buffered. Then `onAlloc` hands libuv the tunnel's scratch, `receiveTunnelRead` feeds the tunnel session and moves what it decrypts into the inner session through the inner layer's scratch (`forwardTunnelPlaintext`, which then runs the usual handshake or decrypt step), and `sendCipherOutput` encrypts the inner layer's output again with the tunnel (`sendTunnelOutput`). `close` sends the inner `close_notify` through the tunnel, then the tunnel's own.

**The handshake.** A client handshake starts in `start_tls` (`Stream.startClientTls`, which `tls_connect` calls after connecting), and a server one on a plain accepted connection in `accept_tls` (`Stream.startServerTls`); both first feed the session whatever the peer already sent (`feedBufferedIntoTls`), since a client hello can arrive right behind the plain-text command that asked for TLS; a server stream from a TLS listener starts it on its first read (`io.readStream`), write or `handshake()` (`ensureHandshakeStarted`). Each arrival of data steps it (`stepHandshake`), sending what mbedTLS produced. Tasks wait in `handshake_waiters`: `start_tls` and `handshake()` callers (woken with nothing, or the mapped `NetError`), and writes made before it finished (their bytes are kept and sent once it's done, or they fail with `IoError.HandshakeFailed`). `finishHandshake` wakes them all; a failed handshake also sets the stream's failure, so reads fail with `HandshakeFailed`. Starting never wakes anyone synchronously: a caller is added as a waiter only after the first step. Verification failures come from `mbedtls_ssl_get_verify_result` flags, checked expired, then wrong host, then untrusted. A second timer per stream (`HandleOwner` kind `stream_handshake_timer`, separate from the read timer) implements `timeout_ms`: when it fires first, the handshake fails with `TimedOut`. `close` wakes the waiters, then sends `close_notify` with a best-effort `uv_try_write`.

**Configs and certificates.** `net::certificate` builds a refcounted `ServerCertificate` (the parsed chain and key, checked to match, plus one server config with a session-ticket key) stored in `EventLoop.certificates` (a `SlotTable`) and owned by a `Resource` (`ResourceKind.certificate`) on `net::Certificate`. Each listener (`Listener.setTlsCertificate`, through `listener_use_tls`, which fails with `InvalidCertificate` when the id doesn't resolve, and `tls_listen` then closes the listener rather than serving plaintext) and server `TlsLayer` retains the certificate while using it and releases it on close; when the GC sweeps an unreachable `Certificate` (or at exit), the table slot is removed and its reference is released, freeing the mbedTLS config once no listener or session holds it. A client gets its own config when it passes `ca` or `verify = false`, owned by its `TlsLayer`; otherwise it shares the trust store's.

**The trust store.** The first verifying `start_tls` without `ca` parks in `TrustStore.waiters` and starts a `LoadJob` on libuv's thread pool. The job makes its own `std.Io.Threaded` and fills a Zig `std.crypto.Certificate.Bundle` from `SSL_CERT_FILE` / `SSL_CERT_DIR` when set, else from the system (`Bundle.rescan`: the distribution's bundle paths on Linux, the system keychains on macOS, the ROOT store on Windows); it touches only its own memory and calls no mbedTLS. Back on the loop thread, `finishLoading` adds each DER certificate to one shared client config and continues every waiter with `startClientTls`; the task stays parked and moves to the handshake waiters. While it waits, the stream has `is_starting_tls` set but no `tls_layer` yet, so `Stream.write` fails with `Busy`, `Stream.isBusy` makes the read natives fail with `Busy` (`HttpError.Other` for http reads), and `stream_handshake` fails with `HandshakeFailed`: otherwise another task's bytes would go out in plaintext and its reads would return unauthenticated bytes. At exit, a job still running finishes and is freed without waking anyone.

## 6. HTTP client and server

`std/http` (`std/http.dsk` + `http.zig`) is mostly Dusk code over the same stream natives `TcpConn` uses, redeclared in `http.dsk` with their own error sets: building the URL and the request head, checking methods and headers (`~is_method`, `~is_header_name`, `~is_header_value`), the deadline (`time::monotonic_ns` plus a `remaining_ms` per step), redirects (a recursive `~follow`, at most `max_redirects` deep) and the retry on a stale connection. `http::Client` is a plain Dusk struct: its `request` / `open` merge headers (`~merged_headers`), join `base_url` (`~joined_url`) and fill an `Exchange`; the module functions build a `Client` from their arguments and call it. A client `proxy` is parsed once per call (`~proxy_of`: credentials cut out of the URL before `url::parse`, encoded with the `~base64` native) into the `Exchange`; `~proxy_for` skips it for local hosts. Through a proxy, `open_connection` connects to the proxy (TLS to it for `https://`), and for an `https://` target sends `CONNECT` and reads the answer's head (`~open_tunnel`) before `~stream_start_tunneled_tls`; an `http://` target is written in absolute form with `Proxy-Authorization`. The pool key adds the proxy and its credentials, so tunnelled, proxied and direct connections never mix. Before parsing, `~start` cuts credentials out of the URL (`~without_user_info`, shared with proxies) into an `Authorization` header unless one was given, and the `~encoded_url` native percent-encodes the bytes after the authority that a URL can't hold. The request body is the `Exchange`'s `?Body` union (`text`, `bytes`, or `stream` with a `BodyStream`); `~body_length` and `~has_stream_body` read it for the head, the retry and the redirect rules. The head's `User-Agent` comes from the `~user_agent` native: `<name>-http-client`, with the package name from `build.zig.zon`, joined at compile time. It goes out in `~send_body` after the head: a `stream` body's `write` runs with a client-side `BodyWriter` (`state = -1`, so the server-closing check is skipped), chunked unless its `length` is set. `~should_send_body` implements `Expect: 100-continue` (streamed bodies, bodies of 1 MiB or more): it waits up to 1 s for any data (`~stream_wait_data`), and when the buffered bytes already start a final status (`~stream_has_final_status`, the parser skips `1xx` heads by itself) the body isn't sent and the stream is marked `is_reuse_forbidden`, which `isReusable` checks. Streamed bodies aren't retried on stale connections, and `307` / `308` aren't followed with one (`~can_follow`). `~send` takes a slot for the target's `scheme://host:port` before using any connection (`~host_slot_take`, `EventLoop.host_slots`, `host_slots.zig`): every client request counts, and a client's `max_connections_per_host` decides whether it waits. A waiter is a `SlotWaiter` (handle owner kind `slot_timer` when `timeout_ms` is set; its timer fails it with `TimedOut`). The stream holds the slot (`host_key`) until it goes back to the pool (`enterPool`) or closes; a released slot goes straight to the first waiter, without being counted down and up again. What's native is parsing, streamed decompression and the pool. `std/url` is separate (`url.dsk` + `url.zig`): parsing, `resolve` and percent-encoding are byte loops in Zig that return offsets or strings, and the `Url` struct is built in Dusk.

**llhttp through a C glue file.** llhttp 9.4.3 comes from the `duskilang/llhttp` fork like the other C libraries. `http_glue.c` owns the `llhttp_t` and its settings and exposes a response parser: `feed_head` runs the parser until it pauses in `on_headers_complete` and reports how many bytes the head took (bytes after it stay untouched); the status, reason and each header name and value are recorded as offsets from the first byte ever fed, since the stream's buffer moves; 1xx heads are skipped (`on_message_begin` clears what was recorded). `feed_body` copies `on_body` spans into an output buffer and pauses in `on_message_complete`, so bytes after the message are never consumed; `finish_body` completes a body that runs until the connection closes, or fails a cut-short one. For a response to `HEAD`, `on_headers_complete` returns "no body" and the pause moves to `on_message_complete`, at the same position. Strict mode, no lenient flags: `Content-Length` with `Transfer-Encoding`, two different lengths, bad header characters and bad chunk sizes are all rejected by llhttp. A body-less message (`Content-Length: 0`, `204`) completes only when the parser is fed once more, even with zero bytes, so body reads always feed.

**Reading responses.** A stream's `HttpReader` holds the parser of its current response and the decoded body (`body` from `body_offset`). Three read modes sit next to the plain ones in `readyOutcome`, and unlike them they change the stream as they go:

- `http_head`: feeds what's buffered and isn't fed yet (`head_fed`), and returns the head's bytes once complete (over 64 KiB is `HeadersTooLarge`; the end of input before any byte is the end, after some bytes `InvalidResponse`). `~parse_head` then re-parses those few hundred bytes with a fresh parser into a flat `[]string` (status, reason, name, value...), turning invalid UTF-8 into U+FFFD.
- `http_whole_body: cap`: decodes everything that arrives into `body`, consuming the framing bytes right away, until the message completes or `cap` is passed (`BodyTooLarge`).
- `http_body: BodyRead` (for `ResponseStream`: bytes, line, all text, all bytes): decodes what arrived, then applies the `ReadSource` rules to the decoded bytes, with "ended" meaning the message is complete. The outcome's `consumed` is kept as `taken` and dropped at the start of the next read, so the returned slice stays valid until the native copied it.

A plain-mode failure is an `IoError`; the head and whole-body modes fail with `HttpError` instead (`ReadOutcome.http_failure`, and `ReadMode.wakeFailure` maps a stream's `IoError` for a parked HTTP read), because those natives declare `HttpError` and the wake's relative id is added to its base ([vm-internals](vm-internals.md) 11.3). Body reads of a `ResponseStream` keep `IoError`, so it fits `io::Reader`.

**Compression.** Both `request` and `open` ask for `gzip, deflate` unless the caller set `Accept-Encoding`. `request` decompresses the whole body with `compression::decompress` (`deflate` as zlib first, then as raw deflate when the zlib header is wrong), with `max_body` as `max`. For `open`, `~stream_decode_body` gives the stream's `HttpReader` a zlib-ng decoder: `httpBodyOutcome` feeds the de-chunked body into `HttpReader.body` as usual, then `decodeBody` moves it through the decoder into `plain`, which is what `pendingBody` and the `ReadSource` rules see (so `read_line` and `read_all` work unchanged). A `bytes` read decodes until `plain` holds at least `max(max, 64 KiB)`, keeping the rest of the compressed body for later reads, so a small compressed body can't expand all at once; line and whole reads decode everything they have. The body has ended only when the message is complete, no compressed bytes are left and the decoder reached the end of its stream (a complete message whose stream isn't finished is `UnexpectedEnd`; bad data is `Other`). A zlib decoder that fails before producing anything is replaced by a raw deflate one. `startMessage` and `releaseBody` drop the decoder, so a pooled connection starts clean.

**The pool.** `EventLoop.connection_pool` maps a key (`scheme://host:port`, plus `verify` and `ca` for `https`) to idle stream handles, newest last, at most 8 per key (adding a ninth closes the oldest). `~pool_put` checks `Stream.isReusable` (no waiter, open, not ended or failed, nothing buffered, the TLS handshake done, the message complete with keep-alive) and closes the stream otherwise; a reusable one gets `pool_key`, drops its buffers, keeps reading, and starts its timer with `onIdleTimeout` (30 s). Anything that arrives while it's idle, data or the end, makes it unusable, and `onRead` evicts it (`evictIfUnusable`): it leaves the pool and closes. Idle streams don't count as pending operations, so they never keep the program running; but since the loop isn't polled while nothing is pending, a close by the server can go unnoticed, so `~pool_take` runs one non-blocking poll before checking `isReusable` on the newest entry. On the Dusk side, a request takes from the pool first; if a reused connection fails with `ConnectionReset` (nothing arrived, or a reset), an idempotent request (`GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS`) is sent once more on a new connection. A followed redirect's body is read (up to 64 KiB) so its connection can go back, and a `ResponseStream` calls `~pool_put` on `close()`.

**The server.** `http::listen` is `net::tcp_listen` / `net::tls_listen` plus a `ServerState` in `EventLoop.http_servers` (a `SlotTable`, its id in the file-only `server_id` of `Server` and `BodyWriter`, owned by a `Resource` of kind `http_server` on `Server`). `Server.serve` is a Dusk accept loop (a method with its own error slot, `serve[E: error]`) that spawns `serve_connection` for each `TcpConn` and counts them, so it can wait for them to finish after `close()`. It also keeps their stream ids in a `map[int, bool]`: once `shutdown_timeout_ms` has passed since the loop ended, it closes every stream still there with `~stream_close` (a stream already closed is a no-op) and returns without waiting more. With `stop_on_signal`, `serve` first opens `os::watch_signal` streams for `Interrupt` and `Terminate` (`~watch_stop_signals`, skipping one that fails with `Unsupported`) and spawns one waiting task per stream (`~close_on_signal`); the first signal closes all of them, which wakes the other waiter with `Closed` and brings back the default action, then calls `close()`. `serve` closes them again before returning, so no waiting task keeps the program running. With `max_connections`, the loop doesn't call `accept()` while the count is at the limit (it checks again every millisecond, and leaves when the server closes), so new connections wait in the system's queue. Since `TcpConn`'s `stream_id` is file-only to `std/net`, `~conn_stream_id` reads it from the struct's first slot. A connection loops over requests:

1. **Wait.** The connection is marked idle in its `ServerState`, then `~stream_wait_data` (the `any_data` read mode: completes as soon as one byte is buffered, consuming nothing) waits `head_timeout_ms` for a new connection, `idle_timeout_ms` for a kept one. `server.close()` removes and frees the `ServerState` and closes every idle stream, which wakes those waits with `Closed`; a connection in the middle of a request isn't idle, so it finishes, and subsequent `server_is_closing` / `server_set_idle` calls see the missing slot as closing.
2. **Head.** `~stream_read_request_head` starts a request parser on the stream (`HttpReader.startMessage(.request)`: `dusk_http_request_parser_new`, which also records the target span and reports the method, version and keep-alive) and reads the head with `head_timeout_ms`; `~parse_request_head` gives `[method, target, version, keeps_alive, name, value...]`. Failures become `400`, `431` or `408` and close the connection.
3. **Handler.** The `Request` is built in Dusk (the path decoded with `url::decode`; an absolute-form target goes through `url::parse`). Body reads are the client's modes on the request parser (`http_whole_body` for `text` / `bytes`, `http_body` for `read_bytes`), failing with `InvalidRequest` because the reader knows its kind. The reader also records whether `100 Continue` went out (`~claim_continue`, sent on the first body read) and whether the body was too large or broken (`~request_body_failure`), which turns an escaping handler error into `413` or `400` instead of `500`. Failures that get a line on stderr go through one `report` function, `serve`'s `on_error` or `~print_failure` when it's `null`, passed down `serve_connection`, `serve_request`, `finish`, `checked_response`, `write_response`, `write_stream_body` and `send_stream_body` as an `http::Failure[E]` (`handler`, `invalid_response`, `streaming`).
4. **Response.** `~request_body_state` says whether the body is complete, unread (then drained up to 64 KiB with `~stream_drain_request_body`), waiting for `100 Continue`, or failed; only complete or drained bodies keep the connection, along with the client's keep-alive and the server not closing. The head is built in Dusk (reason phrases, `Date` from `~http_date`, `Content-Length`). A body of at most 64 KiB is copied after it into one buffer and sent with a single write (`~write_joined`); a larger one goes as a second write. A streamed response (`http::stream`, `http::file`: `Response`'s file-only `stream` function and `stream_length`) sends the head with `Transfer-Encoding: chunked` (or `Content-Length` when the length is known), then calls the function with a `BodyWriter` (`~write_stream_body`): writes collect in a 16 KiB Dusk buffer and go out as one chunk (size line + data + CRLF in one write) when it fills, on `flush()` and at the end, followed by `0\r\n\r\n`. The writer fails with `Closed` for `HEAD`, once the server is closing (`server_is_closing`), or when the stream write fails, so endless streams end at `close()`. `http::file` doesn't go through `fs::File`: it calls the `std/fs` natives directly (`~open_descriptor`, `~file_stream`, `~stream_read_bytes`, redeclared in `http.dsk`), takes the size from the open job's `fstat` as the response length, keeps the handle with its own resource owner (so an unsent response's file is closed after a collection), and reads exactly that many bytes, so a small file costs one open job and one read job.
5. **Compression.** `~write_response` decides it in Dusk: `~is_compressible` (server's `compress`, no handler `Content-Encoding`, a text `Content-Type`), `~accepts_gzip` (the request's `Accept-Encoding` entries, `q=0` refusing), a body to send and, for a whole body, at least 1 KiB (`MIN_COMPRESSED_BODY`). A whole body goes through `compression::compress` at the server's `compression_level` (the thread pool above 256 KiB) and is sent compressed only when that's smaller; `Content-Length` is the compressed size. A stream gets `Content-Encoding: gzip` and chunked framing, and its `BodyWriter` carries a `compression::Compressor` (`is_compressing`): the 16 KiB buffer's contents go through the compressor before framing (`send`, then `send_frame`, which skips empty output), a full buffer only sends what the compressor gives back (`send_pending`), `flush()` also flushes the compressor, and `finish_body` writes the compressor's tail before `0\r\n\r\n`. `~write_stream_body` closes the compressor whatever happened, so an abandoned stream frees its zlib-ng state. Compressible responses get `Vary: Accept-Encoding` whether compressed or not.

`http::listen` defaults to a backlog of 1024, so a burst waits in the system's queue while the accept loop drains it 64 at a time.

## 7. Opened files

`fs::open` runs an `open_file` fs job (`uv_fs_open`, then `uv_fs_fstat` to reject folders and read the size) and returns `[descriptor, size]`; `file_stream` wraps the descriptor in a file-kind `Stream` (`EventLoop.openFileStream`) with `owns_file`, `can_write_file`, `is_append` and `file_offset`. libuv has no `lseek`, so opened files keep their own offset: each `read_chunk` job reads at `file_offset` (advanced as chunks arrive) and each `write_chunk` job writes at the offset of what came before it (`-1`, the OS's end of file, for `Append`, where `file_offset` only counts for `position()`). Redirected stdin keeps reading at the OS position.

Writes go to `Stream.pending_output` (`writeFile`); when it reaches 64 KiB, or on `flush`, `startOutputJob` hands it to one `write_chunk` job (a loop of synchronous `uv_fs_write` on the pool). A writer waits (`output_waiters`) only when a job is already in flight and the buffer fills again; a flusher waits until nothing is pending or in flight. A failed job sets `output_failure`, returned to the waiters or to the next `write` / `flush`. `close` flushes from Dusk first; at exit `releaseAtExit` writes what's left synchronously (`writeOutputNow`), and a job still in flight finishes in `EventLoop.deinit`'s last `uv_run`, whose `finishOutput` writes the rest. `seekFile` refuses while a reader waits (`Busy`) and drops the read buffer; position and size count pending writes.

## 8. Compression

**zlib-ng through a C glue file.** zlib-ng 2.3.3 comes from the `duskilang/zlib-ng` fork like the other C libraries. Its `build.zig` builds the native API (`zng_` names, so nothing clashes with a system zlib) with runtime CPU detection: each SIMD source (SSE2 to AVX-512 and VPCLMULQDQ on x86_64, NEON and the CRC32 instructions on aarch64) is its own object compiled with those CPU features added to the target, and zlib-ng picks the fastest version on first use. `compression_glue.c` is the only file that calls it: a `DuskZip` wraps one `zng_stream` (compressor or decompressor), and `dusk_zip_compress` / `dusk_zip_decompress` take any input and output sizes (they feed zlib-ng 1 GiB at a time, since its counters are 32-bit) and return `DUSK_ZIP_OK` (more to do), `DUSK_ZIP_DONE` (end of stream), `DUSK_ZIP_INVALID` or `DUSK_ZIP_OUT_OF_MEMORY`. The format picks zlib-ng's `windowBits`: 31 for gzip, 15 for zlib, -15 for raw deflate. zlib-ng checks the gzip CRC-32 and the zlib Adler-32 itself. `compression.zig` declares the glue by hand, plus `compressAll` / `decompressAll`.

**Whole buffers.** `compression::compress` compresses into C memory sized by `zng_deflateBound` in one call, then allocates the Dusk buffer once with the result; `decompress` grows a C buffer (4x the input, at least 64 KiB, doubling) and stops one byte past `max` with `TooLarge`, so a small input can't make it allocate without limit. Input left after the end of a gzip stream must be another gzip member (decoded too, as gzip allows); any other leftover, or input that ends before the stream does, is `InvalidData`. Inputs up to 256 KiB run inline on the loop thread and touch `args` only before allocating. Bigger ones run as a `CompressionJob` (`io/compression/compression_job.zig`) on libuv's thread pool: `EventLoop.startCompressionJob` copies the input into the job, queues it with `uv_queue_work` and the calling task parks; the pool thread runs the same `compressAll` / `decompressAll` on the job's own memory, and the done callback wakes the task with the result as a `bytes` payload (a buffer) or a relative `CompressionError` id (`OutOfMemory` on the pool becomes `Other`). A job finishing while the program shuts down is freed without waking anyone. The job file makes no libuv calls; `event_loop.zig` does the queueing.

**Streams.** `Compressor` and `Decompressor` are Dusk structs holding a compression id into `EventLoop.compression_streams` (a `SlotTable(CompressionStream)`), created on their first call so the struct can be built directly (`~compression_id` is `-1` until then). Like the other `SlotTable` ids, a finished or closed stream's id never reaches a stream that later reuses its slot: it fails with `Finished` instead. `finish` (both kinds), `close` and `TooLarge` free the zlib-ng stream and `CompressionStream` at once; anything left is freed in `EventLoop.deinit`. Each `write_bytes`, `flush` and `finish` produces into a growing C buffer (`compressPart`, `decompressPart`) and then allocates one Dusk buffer. A `CompressionStream` also keeps the decompressor's `max`, how much it produced so far, and whether the input ended exactly at the end of a stream (`is_at_end`, which `is_done` and `finish` read; more gzip input after it restarts the inflater for the next member).

**Readers and writers.** `compression::Writer[W]` and `Reader[R]` are Dusk code over a `Compressor` / `Decompressor` (no natives of their own): the writer passes each compressed part to `inner.write_bytes` when it isn't empty; the reader reads 64 KiB from `inner`, decompresses it into `held`, and hands out slices of it, finishing the decompressor when `inner` returns `null`.

## 9. Time and time zones

**Clocks.** `now_ms` and `monotonic_ns` are natives that return a plain `int` without parking. They read `std.Io.Clock.real` for Unix-epoch milliseconds and `std.Io.Clock.awake` for monotonic nanoseconds through `vm.io`, without starting the event loop or allocating. Wall-clock milliseconds floor fractional milliseconds from the `i96` nanosecond reading, and both conversions check the signed `i64` range via `RuntimeErrorReporter.clockOutOfRange`.

**Values.** `Timestamp` (epoch milliseconds), `Duration` (nanoseconds), `Instant` (a monotonic reading) and `TimeZone` (a zone id) are ordinary structs with a private `int` field. The arithmetic natives compute in `i128` and fail with relative `TimeError` variants. The Duration factories call `~scale_nanoseconds`, which reports a runtime error (`DurationOutOfRange`) instead of an error value.

**Zone ids.** A `TimeZone`'s id says what it is. Ids from -86,399 to 86,399 are fixed offsets in seconds (0 is UTC). Ids from 86,400 up pick a zone in the bundled database by its index. The id right after the last named zone means the local zone when it has no name. `timezone.zig` holds the `Registry` on `VM.timezones`. It caches parsed rules by payload, so aliases share rules but keep their own names. Its memory is freed with the VM, error exits included; UTC and fixed zones take none. Nothing in the registry points into the GC heap.

**The database.** `vendor/timezone-data` is a local build dependency holding the pinned IANA release as an index and one file of slim TZif payloads (`zones.bin`), embedded in the binary. Named rules are views into that data. The tools that generate and check it live in the separate `dusk-timezone` repository.

**Reading rules.** `Rules.parse` validates a TZif payload before any view into it is used: lengths, counts, type indexes, offsets, names, flags and ordering. Leap-second data and version 4 aren't accepted. To find an offset, the reader turns milliseconds into seconds (rounding down) and binary-searches the transitions. Before the first transition it uses the first time type; after the last, it evaluates the footer's recurring rule (`timezone_recurrence.zig`). A file with transitions but no usable future rule is rejected, rather than freezing the last offset. None of this parks.

**Formatting.** `time_format.zig` writes ISO text for both `to_iso_string` and `to_utc_iso_string`. The UTC one passes zone 0 and skips the registry. It looks up the offset at that moment and rejects one with seconds (`PrecisionLoss`). It applies the offset in a wide integer, splits the result into calendar fields (`calendar.zig`), and builds the text in a 40-byte stack buffer before allocating the one result string. `format` uses `PatternFormatter` in the same file in two passes. The first pass scans the whole pattern, checks the tokens and brackets, and counts the exact length (checked), so `InvalidFormat` and `PrecisionLoss` are found before allocating. The second pass allocates the result once, rereads the pattern from its argument slot (the allocation can move it), and writes straight into the string.

**Parsing.** `from_iso_string` is `IsoParser` in `std/time.zig`: it reads the fields strictly, checks the calendar date and offset, and converts with the same calendar code.

**The local zone.** The first `local_timezone` call starts a `LocalJob` (`io/time/timezone_job.zig`) on libuv's thread pool and parks. The job reads `TZ` from `VM.environment` when provided (falling back to `uv_os_getenv` otherwise), owns its request memory and a copy of `TZ`, and touches nothing else but the bundled data. It reads a zone file (regular files only, at most 4 MiB), or on Windows asks the system through `timezone_glue.c`. The result is a validated snapshot of rules, a relative `LocalTimeUnavailable`, or an allocation failure. The snapshot travels as `WakePayload.local_timezone`, which is C memory, not a GC root. When the task resumes, `VM.buildWakeValue` installs the first snapshot into the registry and saves its id in `local_identifier`. A later result reuses that id and frees its own bytes. After that, `local_timezone` returns the saved id without parking; a failure saves nothing, so the next call tries again. On shutdown, pending results are dropped, and a task destroyed before resuming frees its unused result. The Windows path checks the configured zone key and its yearly rules before mapping it through the bundled mapping table, and rejects customized settings. Nothing changes the process's own time zone settings.

## 10. OS context and signals

**Arguments and environment.** `Dusk` hands each VM the program's arguments, an optional read-only `std.process.Environ.Map` and the `std.Io` to use. These are borrowed: the host keeps them alive and unchanged while the program runs. The CLI passes the arguments after the script path and its own environment; a program embedding Dusk gets empty ones by default. `os::args` checks UTF-8 and builds the array with `VM.allocStringArray`; `env` and `cwd` copy their text into new strings. `cwd` uses `std.process.currentPathAlloc`. None of these use libuv.

**Exit code.** `os::set_exit_code` only sets `VM.exit_code`. When the program ends normally, `Dusk.runProgram` copies it into `Dusk.exit_code`, and the CLI exits with it after flushing output and tearing the VM down. A failed run exits with 1. An embedded run never exits the host process.

**Signal streams.** A subscription (`io/os/signal.zig`) lives in `EventLoop.signal_subscriptions`, a `SlotTable` like the stream table. The Dusk `SignalStream` holds its handle and an owner (section 14). `Signal` maps to `SIGINT`, `SIGTERM` and `SIGWINCH` (`signalNumber`); on Windows libuv emulates `SIGINT` and `SIGWINCH` (number 28) from the console and has no `SIGTERM`. Each subscription starts a `uv_signal_t` right away and keeps one "signal arrived" flag and at most one parked task. An idle watcher is unreferenced, so it doesn't keep the loop alive. A waiting task references it and counts in `pending_operations`. A signal with no waiter sets the flag; with a waiter, it clears the waiter, unreferences the watcher and wakes the task. A second waiter fails with `Busy`. Closing removes the table entry at once, so the slot can be reused under a new generation. It stops the watcher and wakes a waiter with a relative `OsError.Closed` (unless the loop is shutting down). The handle's `HandleOwner.signal` routes the close callback, which frees the memory. At shutdown, every remaining watcher is closed before its memory is freed.

## 11. Random state

**The shared sequence.** `VM.random_engine` is an optional `Xoshiro256` engine per program, separate from the one maps use for hashing. `std/random` seeds it on first use from 8 bytes of `std.Io.random`. Integers are drawn without bias over the full inclusive range, floats as `f64`, and bytes through the engine's byte interface. No pointer into the engine is kept between calls.

**Generators.** A `Generator` is an ordinary struct with four private `int` fields holding the engine's four state words. Its natives rebuild an engine from those fields, draw, and write the words back. Struct sharing and `copy` give the alias and snapshot behavior for free, with no new heap kind or native table. `generator_bytes` allocates its buffer first and only then reads the state from its argument, since the allocation can move the struct.

**Secure bytes.** `secure_bytes` allocates the buffer, fills it with `std.Io.randomSecure`, and fails with a relative `RandomError.EntropyUnavailable` when that fails; it never touches the shared engine. Both `defaultEngine` and `secure_bytes` fail with `RandomError.Unsupported` when the VM has no `std.Io`. Zero sizes skip the source, and bad bounds or sizes are rejected before any state changes. Buffer sizes are checked before collecting. Nothing here uses libuv or parks.

## 12. Child processes

**Records.** `io/process/process.zig` keeps a `Process` per child in `EventLoop.processes`, a `SlotTable`; a record's handle is its `table_index`, so a stale handle never reaches a later child. The record holds the libuv process handle and an optional timer, the capture pipes or pipe stream handles, the exit status, and at most one waiting task. `process_glue.c` fills libuv's spawn options (stdio modes and pipes) against libuv's own headers, so Dusk doesn't mirror that platform-specific struct; the process handle itself stays opaque, sized with `uv_handle_size`.

**Launching.** The natives check the arguments, folder and environment and copy them into an arena of C memory, since the GC moves objects. A program given as a path is spawned at once with `uv_spawn`. A bare name is looked up on the parent's `PATH`. The native builds the candidate paths, and an `ExecutableLookup` job checks them on libuv's thread pool (`uv_fs_access` and `uv_fs_stat`, like an fs job) while the task waits. The job owns the arena, and its done callback spawns the child on the loop thread. The path it found is what gets spawned, so a child environment with a different `PATH` can't change the lookup. A failed `uv_spawn` still closes its handle asynchronously, so the native's failure path polls the loop once to run those closes; a loop of failing launches then doesn't pile up memory.

**Lifetime.** `live_processes` counts running children and keeps the scheduler going even when nothing is parked: the program waits for them. A launch adds one and the exit callback removes it, stores the status and closes the handle. A record is freed once it's released and all its handles (process, timer, capture pipes) have closed. `EventLoop.deinit` kills the children still running (the program failed) and runs their exit callbacks before the generic handle cleanup. A dropped `Child` is handled by `releaseOnceExited` (section 14). When no task is left but children still run, `VM.runScheduler` calls `EventLoop.closeChildPipes` before waiting, since no task can use those pipes again; otherwise a child blocked on a full or empty pipe would keep the program alive forever.

**`run`.** A captured run uses two raw pipes of its own, each with a fixed read buffer, read into C arrays under one shared byte limit, separate from the stream layer's backpressure. It finishes when both pipes reach the end and the child has exited. The first failure (a read error, too much output, or the deadline) closes the pipes and kills the child, then wakes the task once the exit is seen. The deadline keeps running after the pipes end without an exit, and after an exit with a pipe still open. The parked call returns the record's handle. Dusk code then reads the status and both outputs through allocating natives, builds `Result` and `Termination`, and releases the record. There's no special result object or wake payload.

**`start`.** Interactive pipes are ordinary streams: `Stream.openProcessPipe` creates an unopened pipe that libuv opens during the spawn. A child that inherits stdin shares the program's stdin pipe, so `start` calls `EventLoop.pauseStdinWhenIdle`: the stdin stream stops reading ahead unless a task is waiting on it, and the next read restarts it (`parkReader`). Without that, the stream's read-ahead and the child would race for each new line. They read and write with the usual outcomes, UTF-8 and line rules, write queue, timers and io traits, and their callbacks never touch the `Process`. `wait` delivers the exit code and signal as the `ints` wake payload; errors after parking are relative to the extern's error set. Closing a `Child` after exit closes its remaining pipe streams. Copies of a `Child` hold the same handles, so they share the same process and pipes.

## 13. Serialization plans and derived code
`std/serialization` turns values into formats without runtime reflection: the compiler describes each type once and writes typed code for it.

**Plans.** `SemaAnalyzer.planIndex(type, schema)` builds an `ir.Plan` for every type reachable from a serialized type, memoized by (type, schema) and reserved before its children so recursive types end. Building a plan is the single serializability check (private fields, functions, buffers, tasks, error values and non-string map keys are `InvalidType` with the field path). A struct plan lists its written fields with their outside name, accepted aliases, `omit_null`, declared slot and child plan, plus skipped fields with their defaults; enum and union plans list variant names, aliases and declared names; a type with a whole-type `via` becomes a `.proxy` plan pointing at the other type's plan. Codegen turns `ir.Plan` into `serialization_plan.Plan` (`buildSerializationPlans`), adding struct and union descriptors. A default made only of literals (numbers, bools, strings, `null`, and non-nullable arrays of them — non-empty arrays with nullable element types use a closure) becomes a `Constant` in the plan, which the JSON decoder stores directly; any other default becomes one `$field-default` closure function, appended after `$main`. `serialization::plan_of[T, S]()` is replaced by the plan's index at compile time; the public `std/serialization` natives (`field_name`, `find_field`, `variant_name`...) read `vm.program.serialization_plans` by index and bounds-check it, while the file-private JSON natives index it directly with compiler-emitted plan ids.

**Schemas.** A `schema` declaration is a type of kind `.schema` (the default schema is one with no index), so it fills `S: schema` slots like any type argument; an unfilled schema slot gets the default. Member rules come from the type's own `schema` sections (`type_sections`, recorded when the type is filled in, so generic copies have them) and the schema's blocks; `validateSchemaRules` checks every section and block once, and `planStructure` applies names (`externalName` does the case conversion), aliases, skips and proxies.

**Derived code.** `serialization::decode` and `encode` are Dusk functions calling hidden externs (`derive_decode`, `derive_encode`) whose binding is `.serialization`: they never reach codegen. When sema meets one with concrete types, `instantiateDerivedFunction` checks the format has every method the plan needs (`FormatLacksMethod`, naming the field), then `derivedFunctionName` writes one function per (operation, type, schema, proxy) as Dusk source (`derivedSource`), parses it with `ModuleLoader.parse` in a copy of the `std/serialization` module scope whose source is the generated text, and registers it as a generic function over the format. The generated code reaches user types and `via` functions through hidden file-only names (`derived_type_N`, `derived_function_N`) in that module's root table, and two more hidden externs replaced at compile time: `blank[T]()` (a struct with every slot zeroed by `STRUCT_INIT`, filled field by field and returned only once complete) and `field_default[T, F](index)` (the field's default IR, coerced). Decoding branches on `next_field` with `when` (a `JUMP_TABLE`), keeps a `has_N` flag per field, sets literal defaults inline and queues the others as closures in `pending`, which `decode` runs after the whole input; a proxied value's decoder first runs the closures queued while reading the other type (`~apply_pending_since`), so `from` sees its defaults. Every derived function takes a `depth` and fails past `MAX_DEPTH` (512).

**std/json.** Every call runs in the native engine (`json_codec.zig`: a `Decoder` that pulls tokens from its own `Lexer` as the plan asks for them, and an `Encoder`); the only Dusk code that runs is the user's `to` / `from` functions and the non-literal defaults, and native code never calls Dusk mid-parse. The engine keeps every heap value it is building as a temporary root ([vm-internals](vm-internals.md) section 9.2). `serialization::has_proxies[T, S]()` and `is_proxied[T, S]()` are compile-time bools; `lowerIf` lowers only the taken branch of an `if` on either (outside opaque checks), so a proxy-free type encodes with one native call and no extra work. The `Encoder` writes JSON bytes itself into one byte list kept between calls (freed when it grows past 1 MiB), reserving the longest possible size of each key or string first (6 bytes per escaped byte) so the bytes go straight into place; integers use a digit loop (`writeInt`) and floats use Zig's `{}` format, matching `std.json.Stringify`. A module-level `ArenaAllocator` (`scratch`, also retaining up to 1 MiB between calls) holds temporary encode/decode buffers (the copied decode input, unescaped strings, cycle-detection stacks, large field-seen sets, unknown-key sets seeded once per decode via `hash_seed`, and diagnostic paths). The encoded result is copied into a new string once at the end.

**Proxy sites.** `planIndex` ends with `attachProxySites`. A site is a value position whose plan is `.proxy` (maybe behind a nullable) or a field with a field-level `via`: struct fields (`ir.PlanField.site`), array items and map values (`ir.Plan.item_site`), union payloads (`ir.PlanVariant.site`), and the top value (`ir.Plan.root_site` on `.proxy` plans and nullables of them, with a one-element `[]T` holder as container). `siteFor` collapses chains (a `.proxy` plan whose other plan is a `.proxy` again): the site keeps the innermost plan and its two sema-written functions compose every link. `proxyDecoder` writes `~proxy_into_N(mut target, [index | key | tag,] proxy) -> bool` (calls the `from`s, stores the result: field assignment, `target[index]`, `target[key]`, or the `~set_payload` native for unions; `false` when a `from` fails); `proxyEncoder` writes `~proxy_out_N(value, mut out: []P)` (`array::append(out, to(...))`), shared by sites with the same chain and value type. Each `ir.SiteFunction` lists its closure captures; codegen makes one `$proxy-site` closure function per converter (`siteClosure`) and puts both in the runtime `ProxySite` (`plan`, `decode_function`, `encode_function`, `is_nullable_target`).

**Decoding with sites.** Every non-literal default and every conversion becomes a closure appended to one `mut steps: []func() -> bool` array as its object finishes (children before parents), run in order by the Dusk wrapper after the whole input (the wrapper skips that loop when nothing was queued). At a site the decoder reads the other type into a temporary root, leaves the slot zero (null for a JSON null on a nullable target) and queues the converter's closure with captures `[container, (index | key | tag), proxy value, offset]`; array items are queued once the array is complete, since appending can move it; a proxied top value goes through `decode_proxied` and the holder. A step that returns `false` makes the wrapper call `describe_step` with the root plan, which reads the captured byte offset and rebuilds the path once by re-walking the input with `Decoder.findPath`, writes the `json::Diagnostic`, and then returns `InvalidValue`.

**Encoding with sites.** When `has_proxies` is true, `json::encode` runs three native calls around the `to` functions. `collect_sites` walks the value (`Encoder.visit(.collect, ...)`), protecting each non-null site value as a temporary root using the site closure's declared first capture kind (not `field.plan`, which holds the proxy type for field-level `via`) without allocating, then allocates per site an `out: []P` holder, a `children: []func() -> void` list and a closure `[value, out, children, plan, depth, parent]` over `~proxy_out_N` (`parent` is the queue index of the containing site closure, or `-1` for roots), appended to the top-level list and the run queue. The wrapper runs the new closures (`to` calls), then `collect_nested` walks each new `out[0]` with its plan starting from its captured `depth` so `max_depth` covers the whole proxy chain, checks each newly found heap site against its `parent` chain in `queue` (failing with `CycleDetected` on a repeat) and adds child closures to that closure's `children`; it repeats until nothing new is added, so the rounds equal the proxy nesting depth. `encode_with_sites` then writes with `Encoder.visit(.write, ...)`: at each non-null site it takes the next closure of the current level, verifies that the closure matches the site (same converter function, plan and value) before writing `out[0]` with the site's plan and descending into that closure's children, and checks that every level's closures were all consumed; any mismatch fails with `InvalidValue`.

## 14. Resources the GC closes

The mechanism (a `Resource` heap object holding an id into `EventLoop.resources`, the sweep after each collection) is in [vm-internals.md](vm-internals.md) section 9.3. These std structs carry an owner next to their id field (`~stream_id`, `~listener_id`, `~compression_id`, `~certificate_id`, `~server_id`, or `~handle`):

| Struct | Kind | Owner created in | Released in |
|---|---|---|---|
| `net::TcpConn` | `stream` | `tcp_connect`, `tls_connect`, `TcpListener.accept` | `close` |
| `net::TcpListener` | `listener` | `tcp_listen`, `tls_listen` | `close` |
| `fs::File` | `stream` | `fs::open` | `close` |
| `http::ResponseStream` | `stream` | `http::open`, `Client.open` | `close` (connection back to the pool) |
| `compression::Compressor` / `Decompressor` | `compression` | their first call | `finish`, `close` |
| `process::Child`, and the `PipeReader` / `PipeWriter` it returns (same owner) | `process` | `process::start` | `Child.close` |
| `os::SignalStream` | `signal` | `os::watch_signal` | `close` |
| `net::Certificate` | `certificate` | `net::certificate` | GC sweep (freed once no listener or TLS session holds a reference) |
| `http::Server` | `http_server` | `http::listen` | `close` |
| `sqlite::Database` | `database` | `sqlite::open` | `close` (queued after the connection's pending operations) |

Each module declares `~own(kind, id)` and `~release(owner)` externs bound to the shared natives in `native.zig`. A file stream closed by the sweep starts its pending write job first (`Stream.flushOutputBeforeClose`), so buffered writes still reach the disk. A dropped child that has exited is released at once. One still running has its pipes closed (nothing can reach them, and the child then sees the end of its input or a broken pipe) and is released by its exit callback (`Process.releaseOnceExited`, `should_release_on_exit`): the program still waits for it, as for any running child.

## 15. SQLite

SQLite 3.54.1 comes from the `duskilang/sqlite` fork like the other C libraries. The git tree has no amalgamation (SQLite's build generates it with Tcl), so the fork's `dusk/v3.54.1` branch adds the official release's `sqlite3.c` / `sqlite3.h` / `sqlite3ext.h` and a `build.zig` with `SQLITE_THREADSAFE=2` (a connection is never used by two threads at once, so SQLite skips its connection mutexes), `SQLITE_DQS=0`, `SQLITE_DEFAULT_MEMSTATUS=0`, extension loading, deprecated APIs and shared cache left out, and `HAVE_USLEEP=1` off Windows (otherwise busy waits sleep in whole seconds). `sqlite_api.zig` declares the functions Dusk calls; only `sqlite.zig` and the `version` native call them.

**Connections.** `EventLoop.sqlite` is a `Databases`: a `SlotTable(Connection)`, a `SlotTable(ResultSet)`, the SQLite `WorkerDispatch` (created on the first `open`, 4 threads, 64 outstanding jobs; vm-internals 11.5), the connections waiting for room in the pool, and the last failure of each task. A `Connection` holds the `sqlite3*`, a FIFO of `Operation`s, and the task that owns its open transaction (`transaction_owner`), and runs at most one operation at a time: `submitNext` submits the first ready operation (the head, or the first operation from `transaction_owner` while a transaction is open) when nothing is running, and when the pool answers `QueueFull` the connection waits in `blocked` (room reserved when the connection is created) until any SQLite job finishes. So operations on one connection never overlap and run in call order, while different connections run in parallel. An `Operation` embeds the pool's `Job`; it copies its SQL (or path) as NUL-terminated text and the connection's `sqlite3*` when submitted, so the worker touches nothing else.

- `open` creates the connection record first (its handle is the result), then a worker runs `sqlite3_open_v2` with extended result codes (read-only, or read-write with create unless `create = false`), `sqlite3_busy_timeout`, and `PRAGMA journal_mode=WAL` (not for read-only connections) and `PRAGMA foreign_keys=ON` as asked. A failed open frees the record.
- `execute` prepares each statement of the text in turn (`sqlite3_prepare_v2` with its tail), steps it to the end ignoring rows, and finalizes it. The result is `[changes, last insert id]` as an `ints` wake payload: `sqlite3_total_changes64` before and after, so the count covers every statement.
- `execute_with` takes exactly one statement, prepared through the connection's `StatementCache` (64 entries keyed by SQL text, `sqlite3_prepare_v3` with `SQLITE_PREPARE_PERSISTENT`, least recently used evicted and finalized; a statement followed by another fails with `InvalidSql`). The worker uses the cache while it runs the connection's only operation, so it's never touched by two threads at once. After each use the statement is reset and its bindings cleared. `execute_many` prepares the statement once and loops through every parameter row in a single worker job, checking `is_interrupted` between rows and counting total changes across the batch.
- `transaction` runs `BEGIN IMMEDIATE` (prepared through the statement cache) and sets `transaction_owner` to the calling task when it succeeds, then calls the body with a `Tx` holding the same handle. `Tx`'s methods pass `is_in_transaction = true`; while `transaction_owner` is set, `submitNext` skips operations from other tasks (leaving them queued in order) and runs the owner's operations. A direct call on `Database` (including `close` or a nested `transaction`) from the owner task while the transaction is open is a runtime error (`SqliteDatabaseInTransaction`), since it would wait for itself; a call on a `Tx` after its transaction ended (or from another task) is `SqliteTransactionClosed`. When the body returns, `COMMIT` runs and clears `transaction_owner`, resuming the queue; when the body or `COMMIT` fails, `ROLLBACK` runs, clears `transaction_owner` and keeps the body's or commit's failure message.
- `close` marks the connection closing (later calls fail with `Closed` without parking) and queues a close operation behind the pending ones; the worker runs `sqlite3_close_v2`, and finishing it frees the record. A `Database` the program dropped is closed the same way, with no task to wake (`EventLoop.closeResource`, kind `database`).

**Parameters.** `execute_with[P, S: schema]` encodes the parameters with `serialization::encode` into the file-only `ParamWriter`: one level of struct, each field recording its name (after the schema's renames) and a kind (null, int, float, text; bools as 0/1, enums as their variant name) into plain Dusk arrays. Arrays, maps and unions have no writer methods, so they are compile errors; a nested struct fails with `TypeMismatch`. `~execute_with_handle` copies the arrays into owned `Param`s (`:name` sentinel strings, copied text) before parking, so the GC can move the arrays. The worker binds each by `sqlite3_bind_parameter_index` (`UnknownParameter` when the statement has no such name), text with `SQLITE_TRANSIENT`, then checks every parameter of the statement has a value (`MissingParameter`, also for unnamed `?`). These failures carry a message written by Dusk instead of SQLite's.

**Results.** `query`, `query_with`, `query_one` and `query_one_with` share one operation: prepare through the statement cache, bind, then step every row and copy it into a `ResultSet` (column names once, then per cell its kind (null, int, float, text, blob) and value, text and blobs in one byte buffer), built on the worker with the C allocator. Each cell counts `@sizeOf(Cell)` plus its bytes against `max_bytes` (64 MiB by default, `-1` for no limit); going over fails with `TooLarge` and frees the partial result. The parked call returns a handle into `Databases.results`. In Dusk, `~decode_rows[T, S]` reads the row count and column names, then runs `serialization::decode[T, ~Rows, S]` once per row (`query_one` stops after the first) and frees the result with `defer ~result_free`. `~Rows` binds columns to fields on the first `begin_struct` for a field set (`find_field`, so schema renames apply; a column without a field is ignored; two columns for one field fail), walks them in `next_field`, reports a missing required field through `missing_field` (`MissingColumn`), and reads cells with `~cell_kind` / `~cell_int` / `~cell_float` / `~cell_text` natives on the handle: ints only from INTEGER, floats from REAL or INTEGER, bools from INTEGER 0 or 1, strings from TEXT that is valid UTF-8, enums by variant name. A scalar root (`query_one[int]`) reads the first column. Decoding failures become `TypeMismatch` or `MissingColumn`, with a message naming the column, the row and both types in the `Diagnostic`. The `_with` forms are `[T, S: schema, P]`, so `query_with[Row](sql, @(...))` names the row type and infers the parameters' type.

**Errors and timeouts.** A failing step records the extended result code, a copy of `sqlite3_errmsg` (C allocator, made on the worker) and `sqlite3_error_offset`, shifted to count from the start of the whole text. Finishing maps the primary code to `SqliteError` (`errorOf`) and keeps the message and offset in `Databases.failures` under the woken task; the Dusk wrapper reads them right away with `~error_offset` and `~take_error_message` (which removes the entry) and fills the optional `Diagnostic`. Keying by task means tasks sharing a connection never see each other's messages. SQLite only reports an offset for some errors (syntax errors, "already exists"), not for a missing table. When `timeout_ms >= 0`, the operation starts a libuv timer (`OperationTimer`, `HandleOwner.Kind.sqlite_timer`). If it fires while the operation is running on a worker, the loop thread sets `Operation.is_interrupted` and calls `sqlite3_interrupt` on the connection (thread-safe), so the statement stops with `SQLITE_INTERRUPT` (`TimedOut`); if the operation is still waiting in the connection's queue, it is removed and woken with `TimedOut` immediately. Normal completion detaches and closes the timer.

**Shutdown.** `EventLoop.deinit` calls `Databases.interruptAll` first (`sqlite3_interrupt` on every connection with a running operation), then shuts the worker dispatches down (interrupted operations abort quickly, queued ones are discarded without waking anything), then `Databases.deinit` closes every connection still open on the loop thread and frees operations that never reached the pool.
